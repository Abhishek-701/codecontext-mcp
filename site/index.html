The problem

AI assistants forget your repo every single chat

An LLM can only read what fits in its context window. A real codebase is far bigger, so you end up playing librarian.

Without CodeContext

  • You guess which files matter and paste them in by hand
  • Grep and scrolling GitHub do not plug into agent workflows
  • Pasted code goes stale the moment you edit a file
  • Big files burn tokens and still miss the callers

With CodeContext

  • The agent asks for exactly the symbol, caller or file it needs
  • The index updates on every save, so answers stay current
  • Small structured JSON replaces huge file dumps
  • Find things by meaning, not only by exact name
The idea

Stop handing over the whole book. Give it the index

A book has a table of contents and an index so you never reread every page. CodeContext builds that for code, and keeps it up to date while you work.

Old way

How it works

From a file save to an answer, in six steps

Two jobs run side by side. One keeps the index fresh. The other answers questions from it.

Watch

The watcher listens for file changes with watchdog. It waits 300 ms so rapid saves count as one change, and it only cares about Python, JavaScript and TypeScript files.

Skip what did not change

The indexer hashes the file with SHA-256 and compares it to the stored hash. Same hash means nothing to do. This is what keeps updates incremental and cheap.

Parse

tree-sitter reads the code into a syntax tree and pulls out functions, classes, methods, imports, docstrings and call sites. It never runs your code.

Store

Old symbols for that file are replaced with the new ones. Calls are linked to the symbols they point at, and each symbol gets an embedding vector. Everything lands in PostgreSQL.

Ask

An agent such as Claude calls one of five MCP tools. The FastMCP server checks the input and hands it to the query engine, which runs exact SQL or a vector similarity search.

Answer

A small JSON object comes back: file, line, docstring, callers or similar code. For change history it runs git log on demand, so history is never stored twice.

What it does

Five tools an agent can call

Each tool does one job and returns structured JSON. Errors come back as data with a code, never as a crash.

get_symbol

Definition, file location and docstring for a named function or class.

name, repo_path

find_callers

Every place in the repo that calls a given function or method.

symbol_name, repo_path

get_change_history

Recent commits that touched a symbol's lines, and why they changed.

symbol_name, repo_path, limit

semantic_search

Find code by concept when you do not know the exact name, such as "token refresh".

query_text, repo_path, limit

get_file_outline

A quick map of everything defined in one file, in line order.

file_path, repo_path

Chain them

find_callers, then get_symbol, then get_change_history. One question, three precise lookups.

Benefits

Why it is worth building

Always fresh

The index updates on save, in about a second, so answers match the code on disk.

Fewer tokens

The agent fetches only what it needs instead of whole files, saving cost and context space.

Private by design

Embeddings come from a local model. No code is sent to any outside API to build the index.

Exact plus fuzzy

Precise SQL lookups when you know the name, vector search when you only know the idea.

Works with any MCP agent

Claude Desktop, Cursor and other MCP clients all see the same five tools.

Easy to extend

A new language is one new parser class. The writer, query engine and server stay untouched.
